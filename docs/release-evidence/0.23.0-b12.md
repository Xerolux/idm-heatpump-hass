## Live verification (reference plant, 2026-10-19)

Scope: give the advisor a PV forecast source using the core
Forecast.Solar integration — no account, no API key (Solcast would have
required a registration only the owner can make; that decided the pick).

1. **Forecast.Solar setup (PASS)** — a forgotten entry of a removed
   custom Forecast.Solar integration (schema `inverter_size`/`damping`)
   was deleted after confirming no automations or scripts referenced its
   sensors, and a fresh core entry was created through the config flow:
   the HA-suggested coordinates, declination 25°, azimuth 180° (south),
   `modules_power` 20000 W — the plant's measured AC peak is 17.09 kW
   (2026-10-15), consistent with ~20 kWp. The daily forecast moved from
   27 kWh (ghost entry, ~10 kWp) to a plausible 61 kWh for the next day.
2. **b12 never matched (bug found live)** — with
   `advisor_pv_forecast_entity` pointing at `sensor.power_production_now`
   the PV hours stayed empty. Diagnosis over
   `config/entity_registry/get`: on a real HA the registry entry reads
   `platform: "forecast_solar"` while `domain` is the entity domain
   (`sensor`); the b12 lookup compared the integration against `domain`
   and always fell back. Fixed in PR #566 (platform first, regression
   test pins the live entry shape).
3. **b13 end-to-end (PASS)** — after the b13 HACS update and full
   restart the advisor publishes the hot-water window:
   `advisor_warmwasser_empfehlung` = **13:00–16:00** (Europe/Berlin wall
   clock; stored start `2026-10-19T11:00:00+00:00` UTC), source
   `pv_surplus_forecast`, `expected_pv_kwh: 11.08`, and the
   `dhw_window_20261019` recommendation is active alongside the two
   heating-curve topics. This also completes the b10 evidence item that
   could not be verified then: **window times render in the configured
   time zone** (previously the UTC wall clock).
4. **Logs (PASS)** — no idm-heatpump ERROR/WARNING entries in the system
   log across the updates, restarts and the verified window; debug
   logging was enabled and disabled around the diagnosis.
5. **Heat demand stays unavailable (expected)** — the 24 h heat-demand
   plan needs the heat-loss regression, which is still relearning after
   the b10 building-model version bump; this is the documented one-time
   reset, not a fault.
