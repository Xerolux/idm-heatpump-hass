# Release Candidate Evidence: 0.16.0-rc.5

Status: `BLOCKED`

This candidate fixes one KNX command-handling problem: a second setpoint no
longer disappears when the general cooldown or EEPROM protection is active.
The bridge keeps the newest value and applies it after the guard expires. The
official EEPROM-sensitive register classification, the default 60-second
interval and every underlying coordinator/API safety check are unchanged.

`BLOCKED` remains the correct stable-release verdict. Physical KNX
group-address telegram interoperability, first-export bus load, Navigator 2.0
and Pro coverage, the seven-day soak and final maintainer sign-off remain open.

## KNX and Hardware Scope

The reference installation runs Home Assistant `2026.9.0b0`, an active KNX
tunnelling interface and an IDM Navigator 10 heat pump. Private addresses,
tokens, serial numbers and customer data are intentionally omitted.

Before this candidate was built, the following live checks established the
test boundary:

- the bridge options could be saved and the integration reloaded with an active
  Home Assistant KNX interface;
- a safe profile accepted commands but disabled both outgoing KNX values and
  read responses, and selected only read-only energy objects;
- no IDM group addresses had been imported into ETS, so no address was
  registered for incoming commands and no telegram was put on the KNX bus;
- the normal Home Assistant/Modbus write path changed heating-circuit D's normal
  room setpoint from `22.0` to `23.0`, confirmed it after a poll, then restored
  and confirmed `22.0` after the configured EEPROM interval;
- the same test demonstrated the general five-second cooldown and the API's
  60-second EEPROM guard. Both rejected an early direct write as designed.

This is evidence for the active KNX integration, configuration/reload path,
Modbus transport and write guards. It is **not** evidence that a physical KNX
device can decode or issue the bridge's group-address telegrams.
