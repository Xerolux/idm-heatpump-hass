# Release evidence: 0.27.2

Scope: same-day patch for the hot-water field report
[#713](https://github.com/Xerolux/idm-heatpump-hass/issues/713) — the two
charge-hysteresis entities take the Navigator interface's German names, and
the *DHW does not reach target* health check evaluates the charge cycle
instead of comparing the resting tank with the hot-water setpoint. Prepared
from the maintainer-authorized session on 2026-11-16 that produced the
release; the full local gate set was executed in that session. No submission
to IDM Tools, no firmware observation query and no live-plant replay of the
new check was performed.

## Scope and release decision

- Candidate: `v0.27.2` on top of the 0.27.1 stable; API requirement stays
  `idm-heatpump-api[web]==2.16.2`; minimum Home Assistant 2026.11.0.
- Both fixes are scoped to the report: the naming change touches only display
  names (translations and the generated register reference), and the health
  check stays read-only, opt-in (Smart profile plus the health-monitor option)
  and conservative — without the demand signal it reports unknown instead of
  guessing.
- No new plant write path ships: the change adds passive observation
  (`dhw_demand` edges in the operation analysis) and three registers to the
  always-polled set; all three sit in batches adjacent to already-required
  registers, so the physical Modbus request count does not change.

## Change under test

| Area | Result | Limit |
|---|---|---|
| German charge-entity names (#713) | `dhw_charge_on_temp` → *Warmwasserladung Einschalttemperatur*, `dhw_charge_off_temp` → *Warmwasserladung Ausschalttemperatur*; translations regenerated, register reference rebuilt | Display names only; entity IDs and English names unchanged |
| DHW charge-cycle tracking | `OperationAnalysis` tracks `dhw_demand` on/off edges, the peak tank-top temperature per charge and consecutive charges missing `dhw_charge_off_temp` by more than 1 K; outcomes persist across restarts, the first observation reconciles without inventing a completion | Charge identity follows the demand bit only; a snapshot without it pauses the tracker |
| Charge-cycle health check (#713) | Flags a charge stuck ≥ 90 min below `dhw_charge_on_temp`, or two consecutive failed charges with the tank still below the start temperature; resting/cooling tanks never flag; legacy plants keep the setpoint rule | Grace period and tolerance are fixed constants; validated against the reporter's snapshot and synthetic series, not a live plant |
| Polling plan | `dhw_demand`, `dhw_charge_on_temp`, `dhw_charge_off_temp` join `_ALWAYS_REQUIRED` so the check survives disabled entities | Registers absent from a family's map are dropped as before (`& known`) |

## Interpretation and boundaries

- Rollback to 0.27.1 (which does not contain this fix) restores the setpoint
  comparison and the abbreviated German names; the persisted charge-outcome
  fields are ignored by 0.27.1 and resumed unchanged by a later reinstall.
- What `dhw_setpoint` itself drives on Navigator 10/2.0/Pro stays unconfirmed;
  the finding (observed 46/50/55 °C band on one plant) is recorded in the
  Findings register with that scope.
- The 90-minute stuck threshold sits well above the charge duration the
  reporter's 300 l plant needs (46 → 50 °C); larger plants or heavy concurrent
  tapping were not measured, and the check reports unknown rather than alarm
  whenever the demand bit is unavailable.
