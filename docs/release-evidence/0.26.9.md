## Change under test

| Area | Result | Limit |
|---|---|---|
| Local status sensor (`telemetry_report_status`) | States `not_sent`/`accepted`/`rejected`/`unavailable` with attempt times, failure streak and pending-report flag; local-only, removed with consent | Presentation of local delivery state; not part of the transmitted schema |
| Repair notice | Raised after 7 consecutive undelivered daily reports; self-clearing on the next accepted report; removed on withdrawal/stop | Threshold value is a design choice, not derived from field data |
| HTTP outcome split | Permanent 4xx (except 429) drops the frozen report and clears the pending report ID; 429/5xx/network keep it for the persisted retry slot | Classification follows HTTP semantics; no server-side contract test exists |
| Report-ID stability | The persisted ID is reused when a schema change forces the frozen report to be recomposed | Protects against double counting for schema-change recomposition only; a report dropped after 4xx intentionally starts a fresh ID |
| Cooldown error | `send_telemetry` inside the one-minute cooldown raises `ServiceValidationError` with the remaining seconds | Service UX only; the daily slot and deduplication are unchanged |
| Shared timer | Telemetry and firmware observations fan out from one `cloud_scheduler` per entry | Internal scheduling only; no consent, schedule or schema change |
| Options robustness | `payload()` tolerates a missing consent-timestamp key | Defensive only; the config flow always writes the key |
