# Release evidence for 0.29.0

The owner asked for a review and an improvement of the plant telemetry and of the firmware telemetry. The client was read against the live IDM Tools API on 2026-11-27: the server accepts a plant report only with exactly the seventeen known fields and a firmware query with exactly four, so this release adds no data field and leaves both notice revisions (`idm-telemetry-v3`, `idm-firmware-v1`) unchanged. No server change was made. Three defects were traced in code and fixed: a manual submission was answered as accepted after a permanent HTTP rejection; an aggregate collected under a void consent stayed on disk after a refused start; and a failed firmware check was discarded without a log line or any feedback to the service caller.

Both consent forms now offer an optional heat-pump model as the fallback for controllers that report none; the server's own quality flags had the model missing in every report the owner had reviewed. A changed firmware is compared at the next per-minute check, at most every 15 minutes, and the new diagnostic sensor *Firmware check status* shows each outcome. An independent review before the merge found four more problems that this release fixes: an unusable model text blocked withdrawing consent; saving the telemetry form again re-dated the consent and discarded the window collected since the last report; a firmware change right after startup bypassed the random startup slot; and the new sensor was not routed to the Telemetry subdevice.

On Home Assistant 2026.11.0 the integration passed both coverage gates (98.41% overall and 100% for the config flow) with 3,830 unit tests and all 16 real-Home-Assistant tests. Two POSIX-only tests were skipped on Windows. Strict mypy and ruff check and format (0.17.6) were clean. Regression tests cover every service outcome, the deletion after a refused start, the complete consent gate during collection, the kept consent stamp, the model bounds, the throttled re-check and the status sensor.

Not verified: a plant report that carries an entered model against the live API (the field is unchanged and the server checks it with the same 80-character printable rule), the status sensor on a real installation before the post-release install, and the re-check after a real controller update. The model is self-declared; spelling variants are not normalized. Any additional field is server work first — a new notice revision, renewed consent and a server release — and the server source is under version control nowhere, which should change before such work starts. The seven-day soak remains open.
