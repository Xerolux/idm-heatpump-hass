# Release Candidate Evidence: 0.16.0-rc.3

Status: `BLOCKED`

`BLOCKED` is the expected state for this prerelease evidence record. It carries
forward every open item from
[`0.16.0-rc.2.md`](0.16.0-rc.2.md) — a clean Home Assistant artifact smoke
test, Navigator 2.0/Pro coverage, the seven-day soak and the final maintainer
sign-off — and adds one of its own: the KNX bridge has never been exercised
against a real KNX bus.

This candidate adds one new, opt-in code path over `0.16.0-rc.2`: a KNX bridge
that serves the IDM KNX communication objects through the Home Assistant `knx`
integration. Nothing else changes. Entity IDs, unique IDs, register addresses,
write paths, the device hierarchy and the dependency pins are unchanged, and
the bridge is off by default, so an installation that does not enable it
behaves exactly like `0.16.0-rc.2`.

Because this candidate changes integration code, the seven-day soak clock
restarts here; it does not inherit `0.16.0-rc.2`'s elapsed time.

## KNX Bridge Evidence

New in this candidate. Everything below was verified with unit tests and static
analysis only. **No telegram has ever been sent or received on a real KNX bus.**

| Check | Result | Evidence |
|---|---|---|
| Object catalogue resolves against the library register map | `PASS` | all 654 objects map to a register in `build_register_map(circuits=A–G, zone_modules=10, rooms_per_zone=8)` |
| Every writable object maps to a writable register | `PASS` | asserted over the whole catalogue |
| Object numbers agree with `controller_stats_reference` | `PASS` | the two tables share the KNX object ID space and are cross-checked |
| Group address derivation, parsing and overrides | `PASS` | three-level, two-level and free notation; carry into the next middle group; duplicate and unknown-register overrides rejected |
| Values are published through `knx.send` only | `PASS` | the bridge calls the Home Assistant `knx` integration; it opens no socket and implements no KNX stack |
| Commands are registered through `knx.event_register` | `PASS` | writable objects only; deregistered again on unload |
| Read-only objects reject bus writes | `PASS` | asserted |
| Write-only registers are reachable but never published | `PASS` | `error_acknowledge` is registered for events and never sent |
| Echo suppression and direction filter | `PASS` | an outgoing telegram and a value the bridge just published are both ignored |
| Idle without the `knx` integration | `PASS` | no service call is made and a repair issue is raised |
| Off in web-only mode | `PASS` | setup returns before the bridge starts and logs why |
| Config flow and options flow both reach the step | `PASS` | asserted for both flows; disabling keeps the configured addresses |
| **Live bus behaviour** | `PENDING` | **no KNX hardware, gateway or ETS project was involved at any point** |
| **Datapoint type encoding on the wire** | `PENDING` | the DPTs come from IDM's ETS example project and the register units; no telegram was decoded by a real device |
| **Bus load under a full first export** | `PENDING` | pacing is implemented and unit-tested, but never measured on a physical line |

Objects 384 and 385 (external pump demand) are deliberately absent from the
catalogue: IDM's own labels do not map unambiguously onto
`ext_demand_groundwater_pump_m15` and `ext_demand_groundwater_pump_m15_sw_max`,
and a wrong guess would command the wrong pump.
