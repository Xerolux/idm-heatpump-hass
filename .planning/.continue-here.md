<current_state>

The released add-on baseline is `v0.11.0-beta.1` at `a423f8c`; it uses `modbus-connection==4.0.0a3`, `tmodbus==0.5.0` and the exact API pin `idm-heatpump-api[web]==0.9.1`. <remaining_work>

3. Add lifecycle, FC03/FC04/FC16, locking, retry, short-response, batching, model-detection and write-safety tests for injected and default transports.
4. Fix the existing API Ruff formatting failure in `idm_heatpump/registers.py`, expand cross-repository CI to the transport tests, and run Python 3.12/3.13/3.14, Ruff, strict mypy, build/Twine and clean-wheel tests.
5. Test API 1.0 against older open-pin add-on consumers before publishing.
6. Merge and publish API 1.0.0, then verify the GitHub Release, tag, PyPI artifact and a clean install.
7. Create the real add-on beta.2 implementation branch from `main`. Make `IdmModbusConnectionClient` a thin public-constructor/diagnostics wrapper, move backend error translation to the transport boundary, and remove all private API overrides.
8. Bump only the new add-on to `0.11.0-beta.2` with exact `idm-heatpump-api[web]==1.0.0`; keep `modbus-connection==4.0.0a3` and `tmodbus==0.5.0`.
9. Remove the API-0.9.1-only test skip, run full add-on CI and production-backend smoke, then publish and verify `v0.11.0-beta.2`.

</remaining_work>

<decisions_made>

- Released versions are immutable: do not edit or retag `v0.10.1` or `v0.11.0-beta.1`, and do not yank API 0.9.1.
- API 1.0 remains Home-Assistant-independent. `modbus-connection` and `tmodbus` stay add-on dependencies, not API dependencies.
- API register maps, codecs, decoding, model detection, batching, retry policy and write safety stay in the API; the injected transport owns only connection lifecycle and raw register words.
- The stable API 1.0 path requested by the user must preserve the legacy `IdmModbusClient(host)` Pymodbus behavior.

</decisions_made>

<blockers>

- Strict “only Beta 2 can ever receive API 1.0” isolation is impossible for a stable `1.0.0`, because older add-on tags used open requirements such as `idm-heatpump-api>=0.3.0`/`>=0.3.1`/`>=0.3.3`. A stable 1.0.0 can satisfy those ranges. Backward compatibility is therefore a release gate. If strict resolver isolation is mandatory, the alternative is an API prerelease such as `1.0.0rc1`, which would require changing the current release workflow.
- API `main` currently has an unrelated Ruff 0.16.1 format-check failure in `idm_heatpump/registers.py`.
- API CodeQL Dependabot PRs #70 and #71 update the paired init/analyze actions separately and fail when applied independently; treat them as a pair if they are included at all.

</blockers>

## Critical Anti-Patterns (do NOT repeat these)

- Do not call the API dependency “tmodbus”. `tmodbus==0.5.0` is the add-on backend; `idm-heatpump-api` is the device library.
- Do not claim stable API 1.0 is resolver-exclusive to Beta 2. The old open requirement ranges make that false.
- Do not publish API 1.0 before the real add-on adapter suite runs against the built wheel/source branch.
- Do not keep subclass overrides of API private members as the 1.0 contract.
- Do not change historical beta.1 release notes/evidence to describe beta.2.

<context>

The clean architecture is `idm-heatpump-hass -> idm-heatpump-api -> injected transport`, with direct Pymodbus remaining the API default for old/standalone consumers. The add-on bridge currently works but duplicates the API retry loop and accesses `_lock`, `_max_retries`, `_connection_suspect`, `_record_error_context`, `_ensure_connected`, `_try_reconnect`, `_read_registers` and `_write_registers`. API 1.0 should eliminate that private coupling.

</context>
